# Threat model

Trusted: the host, the gateway, the approval key. Untrusted: the sandbox and the agent (including every web page it reads, and a Claude Code session behind the hook).

**Covered:** prompt injection leading to file reads, offsite navigation, messages or forms sent; leaks of planted canaries through the proxy or through any action the gateway sees; a hijacked agent trying to get a risky action approved, to hide what the human sees, or to avoid the tripwire (tested, below).
**Not covered:** a compromised host; a human approving without reading; data the agent legitimately reads and sends to an allowlisted site; secrets other than canaries (canaries detect, they do not prevent theft of real data); a browser exploit that escapes the container; anything a process running as the same user on the host can do to a localhost API.
**Key limits:** the shared secret is in the firmware (demo grade); the dashboard can approve non-critical actions; the key's 84-character screen shows only the start of a long message.

**This is not a claim that Airlock is secure.** It is a list of attacks that were tried, what happened, and what was changed. The red-team suite is [gateway/tests/test_redteam.py](../gateway/tests/test_redteam.py) (246 tests, part of `make test`, no Docker, no keys), plus the red-team cases in `test_docker_backend.py` (run against the live stack with `make sandbox-test`). Every row was written as a failing test first.

## Method and honesty notes

- The attacker model: controls everything the agent sends (tool calls, field contents, the Claude Code hook's `tool_input`), can write files in the workspace and, in the container, run what a compromised browser could (create links), can read what the dashboard shows, and can send HTTP to the gateway from a web page the person visits. Does not control the host, the key hardware, or the gateway process.
- "Before" is what the first full run of the suite showed against the unmodified gateway: **150 of 244 tests failed**. 16 of those were a typo in my own test (two tool names passed `description` twice), so they are not counted as findings. The rewind-traversal tests were run before that, against the unmodified code, and one of them ("/" as the snapshot id) started copying the host filesystem into the workspace and filled the disk to 1 GB free before I stopped it (about 12 GB of throwaway test directories, deleted; about 16 MB of system-protected copies under pytest's temp folder could not be removed). That is the evidence for that row.
- Where I only added a protection without seeing the hole open, the row says so.

**Numbering note.** Rows 46 and 47 were each used twice (two branches merged). They are now 46a and 47a (the key unplug and replay rows) and 46b and 47b (the `download` rows). Nothing else refers to them by number; every other number is unchanged.

## Trusting the proxy CA (what it buys and what it costs)

To apply the allowlist and the canary scan to **HTTPS**, the proxy has to read the requests, so it terminates TLS and re-signs each site's certificate with its own CA. A client only accepts that if it trusts the CA, so the sandbox's trust store contains it (the certificate; `sandbox/entrypoint.sh`). That is the whole trade, and it has consequences:

- **What it gives us:** HTTPS from the sandbox is scanned like HTTP: a canary in an HTTPS URL, header or body is blocked and reported, an HTTPS request to a host that is not allowed is refused. Without it, either HTTPS would be unreadable (and so unscannable) or non-browser tools would fail every request.
- **What it means for the sandbox:** every TLS connection a client in the container makes through the proxy is decrypted by the proxy. That is the point, and it is also why the proxy and its CA key are in the trusted set: whoever holds the key can read and forge HTTPS for that sandbox.
- **Why the key is kept out of the sandbox:** if the sandbox could read the key, a compromised container could mint certificates for any site and (with a client that trusts our CA) impersonate it, or recover the proxy's view of other traffic. The key is created on the host (`state/mitm-ca/private`, mode 0600 in a 0700 folder, git-ignored) and mounted into the proxy container only; the sandbox mounts `state/mitm-ca/public` read-only, which holds the certificate alone. A live test checks the mounts, searches the container's whole disk for a line of the key, and checks the trust folders.
- **What it does not change:** the CA is trusted *inside the sandbox only*. It is not installed on your host or in your browser, and it is a throwaway demo CA (10-year validity, constrained to sign leaf certificates, `path_length` 0). A pinned-certificate client, or a protocol that is not HTTP inside TLS, is not scanned: `rawtcp=false` makes the proxy refuse unknown protocols, not read them.
- **Chromium** in the sandbox still runs with `ignore_https_errors` (it keeps its own trust store, installed separately). It is an isolated browser with no logins; the request still goes through the proxy and is scanned either way.
- **If the key leaks** (it sits in your `state/` folder on the host, unencrypted): anyone with it can forge HTTPS only for clients that trust this CA, which means only the sandbox container. Delete `state/mitm-ca` and run `make sandbox-up` to make a new one.

Scoreboard (`make scoreboard`): 7 attack pages, **7/7 got through unprotected, 7/7 contained**. New: `attack_07_encoded_exfil.html` (reads a backup that holds a canary, base64-encodes it, emails it): unprotected it leaks a value no human could read in the prompt; protected, the encoded value is caught and the agent freezes. A scripted demo of the mechanism, not a real model.

## Known gaps (not fixed)

- **WebSocket ping/pong payloads cannot be scanned.** What the proxy scans: every text and binary WebSocket message, both directions, as it passes (`websocket_message`: a hit drops the message and cuts the connection), and the close-frame reason after the fact (`websocket_end`: reported, the gateway freezes, but the frame already left). What it does not scan: ping and pong payloads (up to 125 bytes each). mitmproxy 12.3.1 had no hook for them when this was checked live (the strict `xfail` in `test_proxy_websocket_live.py`, row 66); that was **not re-checked** in the overnight session (mitmproxy is not installed there). `test_proxy_websocket.py` now pins our side without mitmdump: the addon has exactly the hooks `websocket_message` and `websocket_end`, and a canary offered as a ping payload reaches no hook. If mitmproxy adds a ping hook, or the addon changes, those tests fail and this paragraph must be updated.
- **The tripwire only catches planted canaries.** It reacts to the fake values and files Airlock planted (and their re-encodings). A real secret that was not planted (a real `.env` elsewhere, a token in a page) is not recognized by it. Real secrets are covered by other layers: approvals for anything that leaves the sandbox, and the egress allowlist and proxy. A hijacked agent that never touches a canary is not tripped by it.
- **Glob through a directory symlink** (was suspected here): proved and fixed, row 76. Remaining limit: the check expands the pattern on disk (first 200 folders), so it is slow on a huge tree.
- **The Docker abort and resume path is untested live.** The freeze abort, the runner's refusal until `resume`, and the start-up probe are covered by unit tests and fakes only; no container was running when they were written (rows 50 and 64). The decision logic (cancel on freeze, nothing starts while frozen, one resume per unfreeze, a failing resume does not block the unfreeze, a crashing backend is an error result) is now also tested against a fake backend (`test_sandbox_abort_backend.py`). What needs Docker and stays UNTESTED: the abort socket across a real `docker exec`, the in-container runner refusing calls until `resume`, killing a real `docker exec` client, `DockerSandbox._runner_command` against a live container, and `make sandbox-test` (last run before the freeze-abort change).
- **Other suspected, not proved:** a `web_task` goal in non-ASCII letters (shown as `?` on the key); an open redirect on the approved site itself; `web_task` hosts that are public names pointing at private addresses (TinyFish fetches from its own cloud, so this is not an SSRF into our network); the live TinyFish cancel call.

- **Shell obfuscation.** A Claude Code `Bash` command is a tripwire only when it names a canary, or a glob/brace pattern or a link that really reaches one. `$(...)`, variables, `eval`, `base64 -d | sh`, ANSI-C quoting and interpreters that build the name are not caught. Every command still needs a person, who sees the command; a person can approve something they should not.
- **Directory-wide reads.** `Glob` and `LS` that only list names are SAFE (DECISIONS 13): the canary file names are visible in a listing. A pattern or path aimed at a canary is a HARD_STOP. A `Grep` is gated only if a canary actually exists below its root.
- **Splits with other characters in between.** Detection joins adjacent fields and ignores separators. A value split across fields with letters inserted between the parts, across several requests, compressed then encoded, encrypted, or hidden in an image is not caught.
- **Proxy limits.** HTTP requests, the CONNECT that opens a tunnel and WebSocket messages (both directions) are scanned; a refused unknown protocol is not reported as an event, only refused. WebSocket scanning ran against real mitmproxy 12.3.1 on the host, not in the compose container. Only what mitmproxy decrypts is scanned (a pinned-certificate client simply fails). The proxy's token path is checked with a stub, not against a live gateway with a token set.
- **Policy judges labels, not effects.** A click on a button whose label is not sensitive but which submits a form is SAFE. The proxy allowlist and canary scan are the backstop.
- **Local processes.** Any program running as the same user can call the localhost API. With no key attached it can approve non-critical and critical actions on the dashboard channel. The Origin/Host checks stop web pages and rebinding, not local programs. Auth0 (optional) and the machine token cover only the endpoints stated.
- **In-flight actions.** A freeze cancels the running action (row 50) and ends a pending approval as a deny. Limits: a browser call already inside Chromium finishes within its own timeout (browser state only); on Docker the abort is UNVERIFIED live; an action that completed a moment before the freeze is recorded as executed, because it was; the abort is requested from the freezing thread and takes effect on the next event-loop turn, so a panic rewind can run a moment before a Docker download's partial file is deleted.
- **Unauthenticated `/freeze`** is deliberate (a denial of service the person can undo; it never makes anything less safe).
- **Key and human.** The secret is in the firmware. The key shows 84 ASCII characters; a long message shows only its start and length. A person who taps without reading is the residual risk. The persisted autonomy sequence number is a file in the state directory; someone who can edit it can reset it.
- **Claude Code** is a gate, not the sandbox ([CLAUDE_CODE.md](CLAUDE_CODE.md)): an allowed edit really writes, an approved command really runs, and a user can turn hooks off.
- **A compromised container** that creates links is handled on the host side for reads of canaries; the container escape itself (kernel, Docker) is out of scope.

- **The download tool** fetches whatever an approved URL returns: the content is untrusted data (it can carry a prompt injection for a later `read_file`), and the 5 MB cap and 20 s limit bound only size and time. The person approves the host and file name, not the content. Allowlist hosts are trusted not to serve hostile files.
- **Chromium** ignores certificate errors inside the sandbox (above).

## Not tested

The physical key (every key test uses a simulated serial port), amd64 and Linux hosts, Windows, concurrent approvals on hardware, a real mitmproxy handling a gateway token, other Claude Code versions, resource exhaustion beyond the body-size limit, timing and side channels, and anything involving a real model deciding to attack (the attackers here are scripts and tests).
